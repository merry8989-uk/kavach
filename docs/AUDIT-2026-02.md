# Audit of the external review

A review of the repository listed eight app improvements, a backend priority
table and a roadmap. This is what was checked against the actual code, what was
real, and what was already handled.

The useful part is the disagreements: two of the claims were wrong, and the
single most specific one — the deletion bug — turned out to be worse than
described.

---

## Backend: the P0 list

| Claim | Verdict | What was found |
|---|---|---|
| **Data deletion bug** | **Real, and worse** | Confirmed and fixed. See below. |
| **OTP delivery sends nothing** | **Real** | `_deliver` was a stub. The endpoint returned a `request_id` and success while no SMS was sent. Fixed with real MSG91 and Twilio adapters, and the endpoint now returns 503 rather than pretending. |
| **Rate limiter is per-process** | **Real** | Confirmed: a module-level dict. Fixed with a Redis-backed limiter, an honest in-process fallback, and `shared_across_replicas` in `/health/ready`. |
| **Shared API token in the APK is risky** | **Real, not yet fixed** | The app still ships one service token. Splitting app authentication from user authentication is a design change rather than a patch, and it is not done. |
| DB consistency across lookup / score / counts | Not verified | Needs a live database to check meaningfully. |
| Reliable offline fallback | Already true on the screening path | `DecideCallActionUseCase` is local-only by construction. |
| Real integration tests | Partly true | There are 111 tests, but they are against an in-process client, not a running stack. |
| Monitoring | Not implemented | Nothing exports latency, error rates or provider failures. |

### The deletion bug, precisely

```python
reports = db.query(Report).filter(Report.reporter_hash == actor).delete()
corrections = db.query(Correction).filter(Correction.number.in_(
    db.query(Report.number).filter(Report.reporter_hash == actor)
)).delete(synchronize_session=False)
```

Two things are wrong, and the review caught only the first:

1. **Ordering.** The reports are deleted on the first line, so the subquery on
   the second line always matches nothing. No correction was ever deleted.
2. **Attribution.** Even with the order reversed it would be wrong: it removes
   corrections *on numbers this actor reported*, which is not the same as
   corrections *this actor submitted*.

Underneath both was a schema problem the review could not have seen:
`identity_corrections` had **no column identifying who submitted a correction**.
The intent was not expressible.

So the fix is three parts: `actor_hash` on the table (migration `0004`), the
route records it, and deletion removes by it — independently of the reports, so
the ordering can never matter again. Three regression tests cover it, including
one where the correction is on a number the actor never reported, which is the
case the old code could not have handled even if the order had been right.

This matters more than a normal bug: a right-to-erasure request that silently
keeps the data is a compliance failure, not a defect.

### The 5-second screening rule

The review is right that `CallScreeningService` must answer within about five
seconds, and wrong that Kavach waits on the network: the decision path is
`BlockRepository` and `ContactRepository`, both local.

But the risk is real for a different reason. There was **no deadline at all**.
The first query after a cold start has to open an encrypted database, and if
anything in that coroutine hung, the response never came and the call simply rang
on — with no record of why.

Fixed with a 2.5 second deadline and a deliberate failure mode: if Kavach is too
slow, the call is **allowed**. Losing a genuine call because our own code was
thinking is worse than letting one spam call through. A second response attempt
is also now a no-op rather than a throw, since `respondToCall` throws if called
twice and a screening service that throws has stopped screening.

## Not done, and not claimed

- **Separating app authentication from user authentication.** Still one shared
  service token in the APK.
- **Hindi/English.** The largest outstanding item from the app list.
- **Monitoring.** No latency, error-rate or provider-failure export.
- **Challenging a wrong spam label.**
- **Nothing here is verified on a device.** The screening deadline and the SMS
  adapters are covered by unit tests and code reading, not by a phone call or a
  delivered message.
